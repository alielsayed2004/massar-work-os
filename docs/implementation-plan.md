# Massar Work OS - Implementation Plan & Discovery Report

## 1. وصف الموجود في المستودع (Current State)
تم فحص المستودع والمستندات المرفقة:
- **المستندات الأساسية**: تم استيعاب `Master Brief` و`Decisions Addendum` و`Design System`، وتم تحديد الرؤية بوضوح (نظام لتتبع مهام الفريق وتسليمات العملاء مع دعم دورة المراجعة الداخلية ونقل المهام).
- **ملفات التصميم**: `massar-design-tokens.css` موجود وتم دمجه مع هيكل التطبيق.
- **الحالة البرمجية الحالية**: تم تهيئة بيئة العمل الأولية مسبقاً وتتضمن:
  - مشروع `Next.js` مع `TypeScript` وإعدادات الـ Routing (App Router).
  - مكتبات `Supabase` (Client, Server, Middleware) تم تجهيزها.
  - صفحة تسجيل دخول مبدئية `login` مع Server Action.
  - ملف `00001_foundation.sql` كمسودة لقاعدة البيانات وهيكلة المستخدمين وصلاحيات الـ RLS.

## 2. الـ Stack التقني (Tech Stack)
- **الواجهة الأمامية والخلفية**: `Next.js` (App Router) + `TypeScript` كتطبيق Monolith.
- **قاعدة البيانات والمصادقة**: `Supabase` (PostgreSQL + Auth + Storage).
- **التصميم**: `Vanilla CSS` باستخدام `massar-design-tokens.css` لضمان هوية مسار بدقة دون الاعتماد على مكاتب جاهزة تعارض الهوية.

## 3. طريقة التشغيل (Run Instructions)
1. **تثبيت الاعتمادات**:
   ```bash
   npm install
   ```
2. **إعداد متغيرات البيئة**:
   قم بنسخ ملف `.env.example` إلى `.env.local` وضع قيم `Supabase` الخاصة بك:
   ```bash
   NEXT_PUBLIC_SUPABASE_URL=your_project_url
   NEXT_PUBLIC_SUPABASE_ANON_KEY=your_anon_key
   SUPABASE_SERVICE_ROLE_KEY=your_service_role_key
   ```
3. **تشغيل قاعدة البيانات**:
   قم بتنفيذ السكربت الموجود في `supabase/migrations/00001_foundation.sql` داخل لوحة تحكم Supabase الخاصة بك.
4. **تشغيل خادم التطوير**:
   ```bash
   npm run dev
   ```

## 4. الفجوات (Gaps)
- لم يتم إعداد ملفات قاعدة البيانات الخاصة بـ Supabase محلياً عن طريق الـ `Supabase CLI` (الاعتماد الحالي على سكربتات SQL يدوية). يمكن معالجة هذا عبر تهيئة `supabase init` لاحقاً إذا تتطلب الأمر تشغيل قاعدة البيانات محلياً.
- ملفات الخطوط `Switzer` و `IBM Plex Sans Arabic` غير متوفرة بعد في مجلد `public` ويجب إضافتها لضمان هوية مسار المعتمدة.
- لم يتم تحديد هيكل "التسليمات والنسخ" (Deliverables & Versions) برمجياً حتى الآن، وهو الجزء الأهم في مرحلة الواجهات.

## 5. قائمة المخاطر (Risks & Mitigations)
1. **تسرب البيانات (Data Leakage)**: يمكن أن يطلع العميل بالخطأ على نسخ داخلية. *الحل:* الالتزام التام بتفعيل RLS في قاعدة البيانات، وعدم إظهار النسخة للعميل إلا إذا كانت محددة بعلامة `shared_with_client = true`.
2. **تضارب نقل المسؤولية (Handover Race Conditions)**: قد يحاول الموظف طلب النقل أكثر من مرة أو للمدير أن يوافق بعد إسناد المهمة. *الحل:* بناء نظام يرفض أي طلب نقل جديد للمهمة إذا كان هناك طلب قيد الانتظار، مع استعمال Optimistic Concurrency.
3. **إدارة الوقت والتوقيت (Timezones)**: إدخال أو عرض مواعيد متضاربة بسبب توقيت أجهزة المستخدمين. *الحل:* معالجة كل الأوقات باستخدام `Africa/Cairo` بشكل صريح في الواجهة، وتخزينها بصيغة `UTC` في قاعدة البيانات.

## 6. خطة المراحل (Phase Plan)
العمل سيتم بشكل تسلسلي عمودي (Vertical Slices)، ولن يبدأ مسار جديد إلا باجتياز المسار الذي قبله:

- **المرحلة 0**: الاكتشاف وتهيئة المشروع وإعداد خطة التنفيذ. **(مكتملة)**
- **المرحلة 1**: بناء هيكلة قاعدة البيانات، إعداد المصادقة، وإعداد الـ UI System المبدئي لتسجيل الدخول.
- **المرحلة 2 (المهام والمواعيد)**: واجهات إنشاء المهام، إسنادها، وإدارتها من قبل مدير الفريق، مع دمج توقيت القاهرة.
- **المرحلة 3 (سير عمل النقل - Handover)**: تطبيق نموذج نقل المسؤولية من الموظف لمدير الفريق وتوثيق الحدث في الـ Activity Log.
- **المرحلة 4 (التسليمات والمراجعة الداخلية)**: رفع الملفات لـ Supabase Storage، إنشاء نسخ التسليم (Versions)، وبناء سير المراجعة الداخلية.
- **المرحلة 5 (بوابة العميل)**: إتاحة زر المشاركة، وبناء واجهة العميل لعرض التسليمات واتخاذ قرار الموافقة أو التعديل.
- **المرحلة 6 (التحسين واللمسات النهائية)**: الإشعارات الدقيقة، والتأكد من مطابقة الـ Design System واختبارات الأمان والصلاحيات بشكل نهائي.
